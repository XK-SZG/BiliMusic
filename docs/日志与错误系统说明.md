# BiliMusic 日志系统与错误系统说明

本文档面向使用者与技术支持，说明 v1.0.21 引入的日志系统与错误系统。

---

## 一、日志系统

### 1.1 入口

「设置 → 系统日志」。

### 1.2 实时日志（无需手动刷新）

点击右上角 **「实时日志」** 按钮即可建立长连接（SSE）。此后后台产生的任何日志
都会**立即**出现在面板中，不需要再点「刷新」。

- 按钮变为「暂停实时」时表示连接已生效；
- 标题旁的圆点显示连接状态（绿色＝连接中，黄色＝正在重连）；
- 面板最多保留最近 3000 条实时日志，超出后自动丢弃最旧的记录；
- 筛选条件变化时连接会自动重连，不会丢失日志。

### 1.3 日志筛选（条件可任意叠加）

| 筛选项 | 说明 |
|---|---|
| 包含关键字 | 只显示包含该关键字的日志；用 `\|` 分隔可表示「任一命中」，如 `下载失败\|Errno` |
| 屏蔽关键字 | 排除包含该关键字的日志，如 `请求\|轮询` |
| 模块名包含 | 按记录器名称过滤，如 `download_service` |
| 日志级别 | 点击某个级别 = **只看这一级**；再次点击同一级别 = 恢复「全部级别」；也可点「全部」按钮 |
| 心跳日志屏蔽 | 分类屏蔽高频噪声，见下表（默认全部屏蔽） |
| 时间区间 | 选择起止时间，只显示该区间内的日志；留空表示不限 |

#### 心跳日志分类

| 类别 | 覆盖内容 |
|---|---|
| **HTTP 请求** | `📡 [请求]` 逐条接口访问日志、`urllib3` / `httpx` 的连接日志 |
| **登录验证** | `auth/status` 轮询、「正在请求 B 站导航接口验证登录状态」、「B 站登录验证成功」、「已清除 B 站 API 缓存」 |
| **前端轮询** | `/download/status`、`/system/events`、`/system/logs/stream` 等高频轮询 |

三类可以分别开关：例如排查登录问题时，只关掉「登录验证」屏蔽即可
（点击对应的类别按钮，按钮由绿色变为灰色表示不再屏蔽）。

面板顶部的「当前筛选」卡片会显示当前生效的条件数量；点击「重置全部条件」可一键恢复。

### 1.4 操作状态栏

筛选器下方有一条状态栏，会显示**最近一次日志操作的结果**（成功或失败 + 时间）：

- 成功时显示绿色，例如「✓ 拉取日志（364 条）」；
- 失败时显示红色并给出**后端返回的具体原因**（例如
  `✕ 打开日志目录 无法打开目录 D:\...\logs；尝试记录：...`）。

任何操作都不会再无提示地静默失败；失败详情同时会打印到浏览器控制台，
便于开发者进一步排查。

### 1.4 一键复制与下载

日志面板右上角：

- **一键复制**：把当前筛选条件下的**全部**日志（不限条数上限）复制到剪贴板；
- **下载 TXT**：导出为便于阅读的纯文本；
- **JSON**：导出为结构化数据，便于脚本分析；
- **清屏**：只清空界面/内存中的日志，磁盘日志保留。

### 1.5 物理日志管理

日志同时写入磁盘：

- 开发环境：`backend/data/logs/`
- 打包环境：`<安装目录>/data/logs/`

**「打开日志目录」** 按钮会直接调起系统资源管理器并定位到该目录。

> 实现说明：后端会依次尝试 `ShellExecuteW` → `os.startfile` → `explorer.exe`
> → `explorer.exe /select,`；若后端（在隐藏窗口方式启动时）全部失败，
> 会自动改由 Electron 主进程的 `shell.openPath` 打开。
> 仍然失败时，目录路径会被自动复制到剪贴板并给出明确提示，便于手动前往。

三项保留策略可在界面上实时调整，**保存后立即生效，无需重启**：

| 配置 | 默认值 | 说明 |
|---|---|---|
| 文件数量上限 | 5 | 超出后删除最旧的文件 |
| 单文件体积上限 | 5 MB | 写满后自动轮转为 `bilimusic-YYYYmmdd-HHMMSS.log` |
| 日志总占用上限 | 25 MB | 超出后按「最旧优先」回收，至少保留一个文件 |

「删除全部日志文件」会删除磁盘上的所有日志文件（含正在写入的文件），执行前需要确认。

### 1.6 时间戳

所有日志的时间均为**本机本地时间**，格式 `YYYY-MM-DD HH:MM:SS`，与系统时间严格同步。
日志面板顶部会显示后端返回的服务端时间，便于核对时区是否一致。

> 历史缺陷：旧版本的内存日志把 epoch 数值直接返回给前端，前端 `new Date(数值)`
> 会把它解释成**毫秒**，于是界面上的日志时间显示为 1970 年。
> v1.0.21 已统一返回带时区的可读时间字符串，该问题不再出现。

## 二、错误系统

### 2.1 触发时机

当软件遇到**会导致业务逻辑终止**的错误（例如下载失败）时，会弹出错误窗口。
错误窗口不会阻塞其他操作，可以稍后处理。

### 2.2 错误窗口包含什么

1. **这是什么问题** —— 用大白话说明刚刚发生了什么；
2. **可能是什么引起的** —— 列出可能导致该错误的原因；
3. **可能可以怎么解决** —— 给出按优先级排序的处置建议；
4. **专业且详细的技术内容** —— 错误编号、错误码、上下文、完整调用栈，
   支持一键复制，便于发给开发者或客服。

### 2.3 可执行的操作

| 按钮 | 作用 |
|---|---|
| **一键修复** | 尝试自动修复该错误。例如 Errno 22 会切换到安全输出模式并清零重试计数；文件损坏会清理残留；空间不足会立即清理缓存 |
| **绕过并继续** | 跳过该错误，业务逻辑继续执行（例如让该媒体保持「未下载」，其余任务照常进行） |
| **下载诊断包 (ZIP)** | 生成并保存诊断包 |
| 「下次不再弹窗」 | 该类错误以后不再弹窗，但仍会记录到日志与错误列表 |
| 右上角关闭 | 关闭弹窗（相当于标记为「已查看」） |

### 2.4 诊断包内容

诊断包是一个 ZIP，文件名形如 `BiliMusic-diagnostic-<错误码>-<错误编号>.zip`：

| 文件 | 内容 |
|---|---|
| `summary.txt` | 人类可读的问题概要，可直接粘贴到聊天窗口 |
| `environment.json` | 运行环境快照：版本、系统、Python、依赖版本、磁盘容量、标准流健康度 |
| `error.json` | 本次错误的完整内容与调用栈 |
| `logs/recent.log` | 最近约 1500 条后台日志 |
| `logs/records.jsonl` | 同样日志的结构化版本，便于程序化分析 |
| `README.txt` | 隐私说明 |

**隐私保证**：诊断包**不包含**你的 B 站 Cookie、SESSDATA、账号信息、媒体库内容
或播放记录；所有文本在打包前都经过敏感信息脱敏。诊断包只保存在你的本机，
需要由你手动发送给开发者——本项目不存在任何自动上传行为。

## 三、常见错误码速查

| 错误码 | 含义 | 是否可一键修复 |
|---|---|---|
| `DOWNLOAD_CONSOLE_IO` | 下载中断：终端输出异常（Errno 22） | ✅ 切换到安全输出模式并重置重试计数 |
| `DOWNLOAD_PARTIAL_FILE` | 下载未完成：媒体文件不完整 | ✅ 清理损坏文件并重置 |
| `DOWNLOAD_FILE_IO` | 下载失败：本地文件读写异常 | ✅ 重建目录并清理残留 |
| `DOWNLOAD_PERMANENT` | 该媒体已达到最大重试次数 | ✅ 清零重试计数 |
| `DOWNLOAD_NETWORK` | 下载失败：网络请求异常 | ❌ 按建议手动处理 |
| `DOWNLOAD_UNKNOWN` | 下载失败：未分类异常 | ✅ 重置该媒体下载状态 |
| `STORAGE_FULL` | 存储空间不足 | ✅ 立即清理缓存 |
| `DATABASE_ERROR` | 数据库操作失败 | ✅ 校验并重建数据库连接 |
| `NETWORK_ERROR` | 网络请求失败 | ❌ |
| `AUTH_EXPIRED` | 登录状态已失效 | ❌ 重新扫码登录 |
| `UNKNOWN_ERROR` | 未预期的错误 | ❌ |

完整的错误百科也可通过接口查看：`GET /api/system/errors/catalog`。

## 四、Errno 22 下载中断问题说明

### 现象

- 下载进行到中途（进度不到 100%）时退出，媒体被标注为「重试下载」；
- 无论重试多少次，甚至彻底删除后手动重试，该媒体始终失败；
- 日志中出现 `OSError: [Errno 22] Invalid argument`，调用栈落在
  `yt_dlp/minicurses.py` → `yt_dlp/utils/_utils.py: write_string`。

### 根因

yt-dlp 在向标准错误流输出进度条时，命中了一个**不可写的控制台句柄**
（后端由 Electron 以隐藏窗口方式启动，标准流在某些时刻是可写性异常的）。
该异常被 yt-dlp 包装成 `UnavailableVideoError`，冒泡到下载流程后被当作「下载失败」。

### 之所以「永远无法修复」的两个叠加原因

1. **异常可复现**：只要触发条件不变，每次重试都会再次命中；
2. **重试计数不重置**：旧版本的「重试」入口不会清零 `download_retry_count`，
   一旦累计失败达到上限，之后每次重试都会在**第一次失败后立刻**被判为
   「失败次数过多，放弃」。

### v1.0.21 的修复

1. **从源头禁用终端渲染**：`noprogress` / `noconsoletitle` / 静默 logger，
   进度数据仍通过 `progress_hooks` 正常回调，界面进度条不受影响；
2. **标准流守卫**：下载期间把 `sys.stdout` / `sys.stderr` 临时替换为永不抛错的守卫流，
   即使有残留写入也只会被丢弃；
3. **启动自检 + 自动自愈**：后端启动时探测标准流健康度；一旦在下载中识别出该类异常，
   会立即切换到安全输出模式并**自动重新排队**，不消耗用户的重试次数；
4. **重试计数重置**：界面上的「重试」改为调用 `/api/download/retry/{bvid}`，
   该接口会清零重试计数并清理损坏残留；同时调整了阈值判断，
   手动重试后不会「一次失败即放弃」；
5. **失败残留隔离**：未完成的文件被移动到 `data/failed_downloads/`，
   不再污染下一次重试（也不再被误判为「下载成功」）；
6. **容器完整性校验**：文件校验不再只看体积，还会检查 MP4/FLV/MKV 等容器头；
7. **yt-dlp 错误上抛**：`ignoreerrors=True` 时 yt-dlp 只打印错误不抛异常，
   现在会捕获其错误信息并抛出可诊断的异常，不再丢失真实原因。
