# BiliMusic 配置说明

本文档说明 `config.yaml` 配置文件中各项参数的含义和使用方法。

## 配置文件位置

配置文件位于项目根目录：`config.yaml`

修改配置后需要重启应用才能生效。

---

## 配置项说明

### 服务器配置 (server)

```yaml
server:
  host: "127.0.0.1"  # 后端服务监听地址
  port: 12180        # 后端服务端口
  debug: false       # 是否启用调试模式
```

#### host
- **类型**：字符串
- **默认值**：`127.0.0.1`
- **说明**：后端服务监听的 IP 地址
- **建议**：保持 `127.0.0.1`（仅本地访问），不要设置为 `0.0.0.0`（允许外部访问）以确保安全

#### port
- **类型**：整数
- **默认值**：`12180`
- **说明**：后端服务监听的端口号
- **建议范围**：10000-65535
- **注意**：修改端口后，前端代码中的 API 地址也需要相应修改

#### debug
- **类型**：布尔值
- **默认值**：`false`
- **说明**：是否启用调试模式
- **影响**：
  - `true`：启用详细日志输出，便于开发调试
  - `false`：正常日志级别，适合生产环境

### 存储配置 (storage)

```yaml
storage:
  download_path: "backend/data/downloads"  # 视频缓存目录
  cache_limit_gb: 10                       # 缓存上限 (GB)
```

#### download_path
- **类型**：字符串
- **默认值**：`backend/data/downloads`
- **说明**：视频缓存文件的存储目录
- **支持**：相对路径或绝对路径
- **注意**：
  - 相对路径相对于项目根目录
  - 确保目录有足够的磁盘空间
  - 目录会自动创建（如果不存在）

#### cache_limit_gb
- **类型**：整数
- **默认值**：`10`
- **单位**：GB（千兆字节）
- **说明**：视频缓存的最大容量限制
- **行为**：当缓存超过此限制时，系统会自动清理最旧的缓存文件
- **建议**：根据可用磁盘空间设置，建议至少 5GB

---

### 调度器配置 (scheduler)

```yaml
scheduler:
  cleanup_interval_hours: 6  # 自动清理间隔（小时）
```

#### cleanup_interval_hours
- **类型**：整数
- **默认值**：`6`
- **单位**：小时
- **说明**：自动清理任务的执行间隔
- **清理内容**：
  - 孤立的缓存文件（数据库中已删除但文件仍存在）
  - 超过缓存上限的旧文件
- **建议**：6-24 小时之间

---

### 下载配置 (download)

```yaml
download:
  max_workers: 3              # 并发下载线程数
  max_retries: 3              # 下载失败最大重试次数
  keep_failed_files: true     # 失败残留文件移入隔离区
```

#### max_workers
- **类型**：整数
- **默认值**：`3`
- **说明**：同时进行下载的最大线程数
- **影响**：
  - 数值越大，下载速度越快，但占用资源越多
  - 数值越小，下载速度越慢，但系统负载越低
- **建议范围**：1-5
- **注意**：过高的值可能导致网络拥塞或被 B 站限流

#### max_retries
- **类型**：整数
- **默认值**：`3`
- **说明**：下载失败后的最大重试次数
- **行为**：超过重试次数后，任务标记为失败
- **建议范围**：2-5
- **注意**：用户在界面点击「重试」时会**清零**该计数并清理失败残留，
  因此历史失败不会导致某个媒体永久无法下载（v1.0.21 修复）

#### keep_failed_files
- **类型**：布尔值
- **默认值**：`true`
- **说明**：下载失败时，把未完成的残留文件移动到 `data/failed_downloads/` 隔离区，
  而不是直接删除
- **作用**：避免下一次重试复用损坏文件导致「永远下载失败」；
  隔离区文件会在用户主动重试时被清理
- **建议**：保持 `true`；磁盘紧张时可设为 `false`（改为直接删除）

### 日志配置 (logging)

```yaml
logging:
  level: "DEBUG"              # 根日志级别
  console: true               # 是否输出到控制台
  file_enabled: true          # 是否写入物理日志文件
  memory_capacity: 20000      # 内存日志条数上限
  max_file_mb: 5              # 单文件体积上限 (MB)
  max_files: 5                # 日志文件数量上限
  max_total_mb: 25            # 日志总占用上限 (MB)
```

#### level
- **类型**：字符串
- **默认值**：`DEBUG`
- **可选值**：`DEBUG` / `INFO` / `WARNING` / `ERROR` / `CRITICAL`
- **说明**：根日志记录器的级别
- **注意**：界面的日志面板可以在此基础上进一步筛选，因此无需为了「看一眼」
  而提高这里的级别

#### console
- **类型**：布尔值
- **默认值**：`true`
- **说明**：是否把日志同时输出到标准错误流
- **影响**：关闭后，打包环境下 Electron 主进程的 `backend.log` 将不再包含后端日志，
  但物理日志文件与界面实时日志不受影响

#### file_enabled
- **类型**：布尔值
- **默认值**：`true`
- **说明**：是否把日志写入物理文件
- **日志目录**：
  - 开发环境：`backend/data/logs/`
  - 打包环境：`<安装目录>/data/logs/`
- **说明**：可在「设置 → 系统日志 → 物理日志管理」中一键打开该目录

#### memory_capacity
- **类型**：整数
- **默认值**：`20000`
- **说明**：内存中保留的日志条数（环形缓冲）
- **影响**：数值越大，界面可回溯的历史越多，占用内存也越大（约每万条约 5-10 MB）

#### max_file_mb
- **类型**：浮点数
- **默认值**：`5`
- **单位**：MB
- **说明**：单个日志文件的体积上限，写满后自动轮转为归档文件
  （命名形如 `bilimusic-20261008-213000.log`）

#### max_files
- **类型**：整数
- **默认值**：`5`
- **说明**：日志目录中保留的日志文件数量上限（含正在写入的文件）
- **行为**：超出后自动删除最旧的文件

#### max_total_mb
- **类型**：浮点数
- **默认值**：`25`
- **单位**：MB
- **说明**：日志目录的总占用上限
- **行为**：超出后按「最旧优先」回收，但至少保留一个文件

> 以上四项均可在「设置 → 系统日志 → 物理日志管理」中实时调整，保存后立即生效，无需重启。

### 数据库配置 (database)

```yaml
database:
  pool_size: 20               # 连接池大小
  max_overflow: 40            # 最大溢出连接数
  pool_timeout: 10            # 获取连接超时（秒）
  pool_recycle: 1800          # 连接回收时间（秒）
```

#### pool_size
- **类型**：整数
- **默认值**：`20`
- **说明**：数据库连接池的常驻连接数
- **影响**：影响并发数据库操作的性能
- **建议**：保持默认值，除非遇到连接不足的问题

#### max_overflow
- **类型**：整数
- **默认值**：`40`
- **说明**：连接池满时允许创建的额外连接数
- **计算**：最大总连接数 = pool_size + max_overflow = 60
- **建议**：保持默认值

#### pool_timeout
- **类型**：整数
- **默认值**：`10`
- **单位**：秒
- **说明**：等待获取数据库连接的超时时间
- **行为**：超时后抛出异常
- **建议**：5-30 秒之间

#### pool_recycle
- **类型**：整数
- **默认值**：`1800`
- **单位**：秒（30 分钟）
- **说明**：数据库连接的回收时间
- **作用**：防止长时间闲置的连接失效（如系统睡眠后）
- **建议**：1800-3600 秒之间

## 配置示例

### 低配置设备

```yaml
server:
  host: "127.0.0.1"
  port: 12180
  debug: false

storage:
  download_path: "backend/data/downloads"
  cache_limit_gb: 5  # 减少缓存上限

scheduler:
  cleanup_interval_hours: 12  # 延长清理间隔

download:
  max_workers: 1  # 减少并发数
  max_retries: 2
  keep_failed_files: false  # 磁盘紧张时不保留失败残留

logging:
  level: "INFO"        # 降低日志级别
  memory_capacity: 5000
  max_file_mb: 2
  max_files: 3
  max_total_mb: 6      # 限制日志占用

database:
  pool_size: 10
  max_overflow: 20
  pool_timeout: 10
  pool_recycle: 1800
```

### 高性能设备

```yaml
server:
  host: "127.0.0.1"
  port: 12180
  debug: false

storage:
  download_path: "D:/BiliMusic/cache"  # 使用独立磁盘
  cache_limit_gb: 50  # 增加缓存上限

scheduler:
  cleanup_interval_hours: 3  # 缩短清理间隔

download:
  max_workers: 5  # 增加并发数
  max_retries: 3
  keep_failed_files: true

logging:
  level: "DEBUG"
  memory_capacity: 50000   # 保留更多可回溯日志
  max_file_mb: 10
  max_files: 10
  max_total_mb: 100

database:
  pool_size: 30
  max_overflow: 60
  pool_timeout: 10
  pool_recycle: 1800
```

## 常见问题

### Q: 修改配置后不生效？
A: 确保已重启应用。配置文件在应用启动时加载，运行中修改不会生效。

### Q: 如何恢复默认配置？
A: 删除 `config.yaml` 文件，应用会自动使用内置的默认配置。

### Q: 可以使用环境变量覆盖配置吗？
A: 当前版本不支持，计划在未来版本中添加。

### Q: 配置文件损坏怎么办？
A: 应用会自动检测并使用默认配置，同时在日志中输出警告信息。

### Q: 日志文件在哪里？占用太大怎么办？
A: 日志位于 `backend/data/logs/`（打包环境为 `<安装目录>/data/logs/`）。
可以在「设置 → 系统日志 → 物理日志管理」中一键打开目录、调整保留上限，
或点击「删除全部日志文件」立即释放空间。

### Q: 下载总是失败，界面提示要「一键修复」？
A: 打开出错弹窗（或「设置 → 系统日志」）查看错误码与处置建议。
最常见的 `DOWNLOAD_CONSOLE_IO`（Errno 22）会自动切换到安全输出模式；
若不确定，可点击弹窗中的「下载诊断包 (ZIP)」把诊断信息发给开发者。
